# 本机 Docker Compose 压力测试方案

日期：2026-10-15。对象：当前工作区中的新资产治理平台。用途：建立可重复的本机性能基线，定位瓶颈，并验证导入导出对在线请求的影响。

本文记录测试设计。负载、数据比例和性能阈值是首轮实验参数，不代表已达到的性能或生产 SLA。旧 Go/SQLite 系统不在本轮范围内。

后续执行状态：2026-10-15的测试因同机实验造成的内存不足而中断，详见[前次执行记录](local-compose-performance-results-2026-10-15.md)。资源释放后已于2026-10-16续跑，进度和实测证据见[续跑记录](local-compose-performance-results-2026-10-16.md)。以下设计参数继续作为续跑依据；执行完成与性能达标分别判定。

## 1. 要回答的问题

1. 在固定数据量、权限范围和资源配置下，列表、搜索、详情及写入的延迟和稳定吞吐是多少？
2. 1 万、10 万行文件的预检、后台处理和完整下载分别需要多久，峰值内存是多少？
3. 导入、导出与统计同时运行时，在线查询下降多少？增加 worker 是否有效？
4. 停止加压后，排队任务能否排空，服务能否恢复，是否产生重复资产、越权结果或丢失任务？

最终产出应包含：环境指纹、各场景原始结果、三轮重复测量、瓶颈证据、适合后续回归的负载点。只说明该台机器和该配置下的表现。

## 2. 按当前实现确定测试重点

| 当前实现事实 | 对方案的影响 | 代码依据 |
| --- | --- | --- |
| 资产和任务业务通过 HTTP 调用 IAM 实时授权；授权客户端超时 5 秒 | 公共请求必须经过 Gateway 和真实 IAM；单独观察 IAM 延迟与数据库压力 | [授权客户端](../../platform/internal/asset/auth.go) |
| 资产列表使用 `LIMIT/OFFSET`，搜索为多个字段的 `%关键词% ILIKE`；公共分页上限 100，非法 limit 回落到 20 | 分别测试首页、深分页、不同命中率搜索；显式设置 limit 并校验返回内容 | [资产查询](../../platform/internal/asset/store.go) |
| IAM、资产服务各自的 PostgreSQL 连接池上限为 10 | 区分 CPU 瓶颈、数据库锁等待和连接不足；不能假定增大并发就能增大吞吐 | [IAM 连接池](../../platform/internal/iam/postgres.go)、[资产连接池](../../platform/internal/asset/store.go) |

| `reporting/asset-counts` 依次读取七类可见资产，再写统计结果 | 统计是独立重请求场景，单列吞吐和内存，不混入普通查询的平均延迟 | [统计实现](../../platform/internal/taskcenter/reporting.go) |

| Gateway/任务 API 的请求体上限 100 MiB；HTTP 服务 Read/WriteTimeout 均为 30 秒 | 上传字节包括 JSON 包装和转义；长预检与下载可能先碰到 HTTP 超时 | [部署配置](../../compose.yaml)、[HTTP 服务](../../platform/internal/servicekit/server.go) |
| 资产服务外层默认请求体上限1 MiB，内部批量解码器允许8 MiB | 外层上限先起效；宽记录即使CSV预检通过，500行内部提交仍可能被拒绝，需单列验证 | [配置](../../platform/internal/servicekit/config.go)、[内部接口](../../platform/internal/asset/internal_http.go) |

[已有验收记录](../architecture/amqp-worker-publisher-acceptance.md)中的 10 万行责任部门导入为单次 19.57 秒，环境是两个 worker、合计 4 slots。计时包含上传、预检、确认、排队、执行和轮询，不含 CSV 生成、登录、重放及数据库对账。该值只能作为历史参考；新基线要重新测量，不能作为 p95 或生产容量。

## 3. 环境固定与隔离

使用独立 Compose 项目 `asset-amqp-perf`，保持现有服务拓扑与默认超时。测试环境文件约定为仓库根目录 `.env.perf`，复制自 `.env.example` 后填写独立测试凭据；该文件匹配现有 Git 忽略规则。

建议使用以下宿主端口，启动前检查占用：Gateway 59080、Web 59088、PostgreSQL 59432、AMQP 59672、RabbitMQ Management 59673、MinIO 59900、MinIO Console 59901。通过已有环境变量设置，所有脚本同时传入相同的 EnvFile、ComposeProject 和 BaseUrl，避免连接到开发实例。独立项目使用独立命名卷；仅复用 Compose 文件，不复用开发数据。

每次保存以下环境指纹：

- Git HEAD、工作区 diff 与新增源码清单及文件摘要；本工作区包含未提交改动，单记提交号不足以复现。
- Docker/Compose 版本、镜像 ID/digest、构建 Go 版本、k6 版本。
- 宿主 CPU/逻辑核、物理内存、磁盘类型及可用空间；Docker Desktop/WSL 实际 CPU、内存、swap 分配。
- 进程与副本数量、worker slots、PostgreSQL 配置、各进程连接池设置、对象保留期。
- 数据集编号、总行数、可见行数、文件字节数、种子和启动时队列/任务状态。

方案设计时普通权限未能读取 CIM 硬件信息或访问 Docker daemon；执行阶段已取得资源和版本记录，详见执行记录。实际额度以每轮归档的环境指纹为准。

首轮保留当前 Compose 的资源配置，记录实际额度；例如宿主资源允许时可固定 Docker 为 4 vCPU/8 GiB，但这只是可选实验配置。压测期间保持电源、资源额度及其他前台负载一致，提前完成构建与拉取。k6 在 Windows 宿主运行，访问 `http://127.0.0.1:59080`；它仍与 Docker 争用物理资源，必须采集压测进程自身的 CPU/内存。

## 4. 数据集、账号与可重复性

| 数据集 | 规模与内容 | 目的 |
| --- | --- | --- |
| D0 | 七类资产合计 1 万行，固定随机种子，覆盖字段类型、枚举、中文和空值 | 调试脚本、建立低负载参考 |
| D1 | 七类合计 10 万行；每类先分配 10%，其余 30% 放在责任部门，共 40% | 首轮固定主数据集；此分布是实验假设 |
| D2 | 七类合计 30 万行，沿用 D1 比例；D1 完成且内存/磁盘有余量时执行 | 观察数据增长影响 |
| F1 | 独立的责任部门两字段 CSV，1000/1万/10万行 | 与已有容量链路对齐，便于重现 |
| F2 | 包含更多合法字段、中文、带引号/换行备注的 CSV，1万/10万行 | 验证宽记录、转义后字节数与内存影响 |
| E1 | 独立小文件：必填缺失、非法枚举、重复幂等请求 | 验证失败处理；不计入正常性能分布 |

种子清单保存资产类型、ID、版本、拥有者、部门、软删除状态和预期统计数量。为 10% 的记录预置 5 个版本，为 5% 的记录做软删除，明确数据集总量同时包含软删除记录，并分别记录有效行数。写入按 Schema 生成合法值；大备注也必须符合对应字段约束。

续跑中发现准备阶段的两项限制后，种子工具将系统信息导入文件拆为最多250行，并将准备并发默认设为2。数据总量、字段值和比例保持不变；正式API到达率不受该参数影响。实际失败现场、参数和工具版本见续跑记录，准备失败不并入正常API延迟。

建立三层 IAM 部门树和至少 20 个测试账号，覆盖 admin/reporter/reviewer/auditor 及 own/department/descendants/global。资产类型“责任部门”与 IAM 的部门组织树是不同数据，不能混用。按对应账号生成或导入自有资产，避免所有数据都归管理员，导致普通用户只查到空集合。查询账号按实际可见数据分层报告；写入只使用有权账号。

会话处理必须满足以下条件：

1. 完成首次改密，再登录业务接口；登录与种子准备不计入业务基线。
2. 每个 VU 使用独立登录会话与 Cookie jar；账号可复用，会话不能共用轮换中的 Refresh Token。
3. Access Token 有效期为 15 分钟；按 `expires_in` 提前约 60 秒、加入抖动刷新，单个会话内串行刷新。认证请求独立打标签并计入总网络流量，不并入资产操作延迟。
4. 预置写入记录分配给单一 VU，更新使用其持有的当前版本并保存响应中的新版本。版本冲突另设场景，不在主负载中把意外 409 视为成功。

每轮导入使用 `run_id + 文件编号` 作为幂等键，业务字段带固定长度测试前缀。只有幂等场景才重用同一个键。每轮对比从相同数据快照或等价的新项目卷开始；恢复时 PostgreSQL 与 MinIO 对象引用保持一致，并确保没有旧的待执行消息。不能不断向同一个库追加 10 万行后直接比较耗时，也不能依靠软删除恢复原始物理规模。

## 5. 工具和负载模型

采用本地 k6 编写 HTTP 场景，PowerShell 编排现有 Compose/容量脚本并收集结果。第一版使用已有日志、Docker 资源采样、数据库只读观测及任务指标；Prometheus 可作为后续采集器，当前仓库没有完整的 HTTP/数据库 exporter，不假设已经部署。

普通接口找吞吐拐点使用固定到达率：1、5、10、20、40、80 次业务请求/秒，达到停止条件后不再升档。每档先预热 1 分钟，再记录稳态 3 分钟。一个受控迭代执行一个业务 HTTP 请求，额外刷新、轮询、版本读取分别计数；多步骤事务的 iterations/s 不直接标成 RPS。固定 VU 加 1～3 秒操作间隔只用来补充模拟用户操作，不据此换算“支持多少在线用户”。开放与闭合模型的区别见 [k6 官方说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)。

初次分配 VU 参考 `目标迭代率 × 迭代耗时预算 × 1.5` 向上取整，再用低负载校准，设置本机可承受的上限。必须记录实际请求数、实际到达率及 `dropped_iterations`；掉迭代时先判断是服务变慢、VU 不足还是压测进程饱和，不能只看成功请求的延迟就认定达到目标负载。[k6 指标定义](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)

主混合负载按业务请求数分配：列表 35%、详情 25%、搜索 15%、版本历史 5%、创建 10%、更新 10%。各类型/权限层分别打标签。统计、登录、大文件上传下载和任务轮询另设负载通道，避免少量重操作掩盖普通接口表现。

## 6. 场景矩阵

以下路径均以 `/api/v1` 开头。所有性能流量经过 Gateway，不绕过授权。

| 编号 | 场景与接口 | 负载与样本 | 断言和重点 |
| --- | --- | --- | --- |
| S0 | 登录、列表、创建→查询→更新→版本、导入→确认→完成、导出→下载 | 单用户，D0，每条链路一次 | HTTP 状态、响应结构、权限和数量正确后才能加压 |
| S1 | `GET /assets/{type}`、`/{id}`、`/{id}/versions` | D0/D1；按 1→80 RPS 阶梯；每种端点先单测 | 每端点 p50/p95/p99、错误、IAM/数据库耗时；返回预期非空数据 |
| S2 | 列表深分页与搜索 | limit=20/100；offset=0/1000/10000，以及可见集合末页；搜索命中约 0%/1%/50% | 末页按该用户可见行数计算；分别记录索引、扫描与排序成本 |
| S3 | 按上述 80% 读、20% 写比例混合 | D1；阶梯找稳定点，在候选稳定点独立重复 3 轮，每轮稳态 10 分钟 | 读写分别统计；版本正确；记录测试期间新增资产和版本数量 |
| S4 | `GET /reporting/asset-counts` | D0/D1；0.1→0.2→0.5→1 RPS，每档稳态 3 分钟；global 与小部门各一组 | 七类数量正确；统计服务和资产服务内存；低样本不报告有说服力的 p99 |
| S5 | `POST /import-jobs` → `POST /import-jobs/{id}/confirm` → `GET /tasks/{id}` | F1 三种行数各顺序跑 3 次；再测 1/2/4 个同时在途任务，8 个作为可选排队实验；F2 先单任务 | 分离预检与后台耗时；提交行数、资产和幂等记录对账；默认 attempt=1 |
| S6 | `POST /export-jobs` → 查询任务 → `GET /export-jobs/{id}/download` | 固定 D1，可见集合分别约 1万/10万；在途任务 1/2/4；每组 3 轮 | 完成后下载并解析 CSV；数量、权限、字段及内容摘要正确；下载独立计时 |
| S7 | 在线流量与后台任务混跑 | S3 的稳定负载取 60%；分别加 1 个10万行导入、1 个10万行导出、两者并行；统计另加 0.2 RPS | 对照无任务时同负载的延迟；记录后台吞吐、峰值内存与排队情况 |
| S8 | Worker 扩容比较 | 同一数据快照与任务批次，对比 1副本×2slots、2副本×2slots；资源固定 | 测任务总耗时、完成任务/分钟、行/秒及在线延迟；扩容不一定提升性能 |
| S9 | 突发与持续运行 | 突发：60%稳定负载5分钟→120%稳定负载30秒→60%负载5分钟；持续：60%负载60分钟 | 突发后的恢复时间；持续阶段刷新会话、内存趋势、排队和连接泄漏 |
| S10 | 并发正确性与恢复，独立运行 | 10个请求同幂等键、10个写入同版本；可选在低负载下停RabbitMQ或杀一个worker | 同幂等键只有一个任务/一份副作用；同版本一次成功，其余409；恢复后对账 |

S5 的“同时在途”指创建至最终状态尚未结束的任务数，不等于 worker 执行数。另做短时间同时上传以测预检竞争，并单独标注，不能把纯 worker 饱和与 API 预检竞争混为一组。

S6 的正式数量对账使用冻结的可见集合；当前导出跨多页读取，不应假定具有数据库快照一致性。S7 若一边向同一资产类型写入一边导出，数量变化应单列分析。首轮混跑选不同类型或互不相交的数据范围，使导出预期集合固定。

S10 的故障前后样本不并入正常延迟分布。现有 [故障冒烟](../../scripts/amqp-compose-fault-smoke.ps1)会主动停止基础设施并强杀 worker，可单独复用；它只接受 `asset-amqp-*` 项目。正常压测不默认调用它。

## 7. 异步任务的计时与对账

### 7.1 时间口径

客户端使用单调计时器，同时记录 UTC 时间用于关联日志；报告时间显示为 Asia/Shanghai。

| 指标 | 起止与限制 |
| --- | --- |
| 导入预检耗时 | 创建导入请求发送前 → 收到完整响应；包含 JSON 上传、对象存储、预检与任务存储 |
| 确认耗时 | 确认请求发送前 → 收到完整响应；后台可能在响应返回前启动 |
| 确认到完成耗时 | 确认请求发送前 → 首次观察到 succeeded；包括排队、执行、重试及轮询误差 |
| 导入完整耗时 | 创建请求发送前 → 首次观察到 succeeded；排除生成文件、登录和事后对账；确认应立即发起并记录间隔 |
| 导出生成耗时 | 创建导出请求发送前 → 首次观察到 succeeded |
| 下载耗时 | 下载请求发送前 → 收完响应体；另外记录字节数和 MiB/s |
| 导出完整耗时 | 创建导出请求发送前 → 收完下载响应体 |
| 单次执行耗时 | worker 的 `task succeeded` / `task execution failed` 日志 `duration_ms`，与对应 task_id 关联；指标直方图为聚合补充 |

每个在途任务每 2 秒轮询一次，加随机抖动，独立标记 `task_poll`。N 个在途任务约增加 N/2 RPS；轮询时间、HTTP 耗时及最终超时都保留。超过客户端等待上限记为未完成，不从成功率分母排除，也不直接认定服务已取消。

当前 DTO 没有不可变的 `queued_at/started_at/completed_at`，`updated_at` 会被续租和状态更新覆盖。首轮可以采样确认后首次出现 `running && attempt>=1` 的时间作为排队观察值，但短任务可能完全漏采；不能给出精确的逐任务排队 p95。无重试任务可用确认到完成耗时减执行日志耗时估计排队加通信/轮询开销，明确标注估算。若要精确拆分，需要另行增加结构化的入队/认领时间事件，公共 DTO 不必暴露内部执行 token。

现有 [容量脚本](../../scripts/phase3-capacity.ps1)每秒轮询、最多等待10分钟，只输出一个端到端耗时。复用结果要保留这一口径；它不能直接提供预检/排队分解，也不能支撑超过15分钟的会话或多轮并发场景。

### 7.2 正确性判定

- 新建且无故障的 N 行合法导入：最终 succeeded、attempt=1、committed=N、created=N、skipped=0。
- 用测试 task_id 在数据库只读对账：`asset.import_idempotency`、已提交 `task_report.import_rows` 均为 N；关联资产和版本记录数量正确，抽查中文、枚举、空值。测试核验可跨 Schema 查询，业务服务调用边界保持不变。
- 重放同一个任务幂等键：任务 ID 相同且 `created=false`；行级幂等、资产及版本记录不增加。故障重试后的 created/skipped 按“本次尝试”解释，以累计 committed 和实际唯一资产数为最终依据。
- 用 CSV 解析器检查导出数据行数，不用文本换行数代替；带换行的字段仍是一行。校验所有者权限、敏感字段处理、表头和确定性样本；稳定快照下可规范化顺序后计算内容摘要。
- 停止加压后逐一核对本轮 task_id，不能只依赖最多返回100条的任务列表。未完成、dead_letter、cancelled 与预期成功分别报告。
- 计划内403/409/429仅在对应权限/冲突/错误登录场景视为预期；正常成功场景中的这些响应仍是异常，5xx、超时和业务断言失败不能被排除。

## 8. 指标采集与瓶颈判断

客户端保存每端点、资产类型、权限层、数据集、阶段的请求数、成功业务数、错误率、p50/p95/p99/max、发送接收字节和实际RPS。动态ID不作为指标标签；错误样本保留 request_id，逐任务文件保留 task_id。预热与稳态分开，成功/失败延迟分开，同时保留包含失败的总分布。

k6 的 `http_req_duration` 不包含首次DNS/建连时间，用户完整操作另用自定义计时。校验业务响应并设置 `checks` 或自定义业务失败率的 threshold，仅写 check 不会让测试进程失败。[指标定义](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)、[阈值说明](https://grafana.com/docs/k6/latest/using-k6/thresholds/)

| 层级 | 周期 | 现有来源与关注点 |
| --- | --- | --- |
| 压测进程、宿主、容器 | 5秒 | k6 CPU/内存；Docker stats 的 CPU、内存、网络/块IO；宿主剩余内存和磁盘；记录 CPU 百分比的核数口径 |
| HTTP 各服务 | 连续日志 | 现有请求日志包含服务、path、status、duration_ms、request_id；区分 IAM、asset、task-report；Gateway 延迟包含上游等待，不重复相加 |
| PostgreSQL | 5～10秒 | `pg_stat_activity`、锁等待、活动/等待连接、事务与死锁计数、缓存/读写；慢 SQL 在独立复现阶段取执行计划 |
| publisher/每个worker | 5秒 | 容器网络内的8085/8086 `/metrics`，逐副本抓取；本地可用 compose exec 验证；不额外公开内部端口 |
| RabbitMQ | 5秒 | Management 只读观察 ready/unacked、consumer数、入队/ACK速率、连接、内存和磁盘告警 |
| MinIO | 5秒/任务级 | 容器资源、磁盘增长、请求错误、下载实际字节；没有现成操作耗时指标时用日志或明确补采 |

任务指标直接使用 [已实现名称](../../platform/internal/taskcenter/metrics.go)：

- `taskcenter_outbox_pending`、`taskcenter_outbox_oldest_pending_age_seconds`：发布积压及年龄；包含延后重试，不能等同于可立即执行队列。
- `taskcenter_amqp_confirm_failures_total`、`taskcenter_amqp_return_failures_total`、`taskcenter_amqp_nack_failures_total`：发布异常。
- `taskcenter_worker_active_executions`、`taskcenter_amqp_unacked_deliveries`、`taskcenter_worker_execution_duration_seconds`：执行并发和尝试耗时；后者包含放弃的执行，不是成功任务端到端耗时。
- `taskcenter_worker_claim_conflicts_total`、`taskcenter_worker_lease_expirations_total`、`taskcenter_expired_executions`、`taskcenter_dead_letters`、`taskcenter_quarantined_messages`：争抢、恢复和异常数量。

数据库 gauge 在多副本间重复，按 max/去重；进程 counter、直方图和本进程 unacked 才按实例聚合，处理重启导致的计数重置。死信/隔离看本轮增量。指标抓取返回503或缺失时记录观测缺口，不能填成0。连接池等待、Go GC/heap、PostgreSQL语句统计目前没有完整现成采集；只有需要进一步定位时再加采集，改变配置后另建基线。

定位时先形成可验证假设：IAM延迟同步升高→查授权链路；搜索/深分页特异变慢→查对应SQL；asset连接/锁等待升高→查查询与批次事务；Outbox年龄上涨但worker空闲→查publisher/Broker；worker满载且ready增长→查执行吞吐；统计/导出时RSS陡增→查全量记录及CSV缓冲。每次只改变一个参数，再重复同一场景。

## 9. 首轮参考阈值与停止条件

以下为本机初始参考线，需要与实测一起保存；若低负载已不满足，也应报告真实基线与瓶颈，不能改阈值掩盖失败。

| 项目 | 首轮参考线 |
| --- | --- |
| 普通列表/详情/版本 | p95 ≤ 500 ms，p99 ≤ 1 s |
| 搜索/深分页、创建/更新 | p95 ≤ 1 s，p99 ≤ 2 s |
| 统计 | 单列，p95 ≤ 5 s；请求样本不足时仅报告原始值/中位数/最大值 |
| 正常业务请求 | 非预期错误率 < 1%；越权、丢失提交、重复资产和错误内容容忍度为0 |
| 目标负载兑现 | `dropped_iterations=0`，稳态实际业务到达率在目标±5%内；不满足则该档未证明达标 |
| 导入/导出 | 正常样本全部成功且数量对账通过；首轮不凭空设文件p95，记录各规模三次的中位数、范围和峰值内存 |
| 混跑影响 | 同端点p95较同负载无任务对照增长不超过30%，并保持上述错误/正确性条件 |
| 后续版本回归 | 相同环境与数据下，中位吞吐下降>15%或p95上升>20%触发复核；结合三轮波动判断，不自动解释为代码退化 |

每端点至少100个有效样本才将p95用于首轮比较，至少1000个才比较p99，仍须注明样本数与不确定性。样本不足时延长该档稳态时间，或只报告描述性结果，不宣称达到对应分位数门槛。三次文件实验只报告三次明细/中位数/范围，不称为可靠p95；不得把不同端点的p95简单平均。

`R*` 定义为某一明确负载组合在三轮稳态复测中均满足参考线、负载兑现和正确性要求的最高已测试RPS。只报告已验证点，不外推未测试区间；不同数据集/权限/组合分别有自己的R*。常规回归使用约 `0.6 × R*`。若80 RPS仍全部通过，结论为“已验证至80 RPS，尚未找到上限”，不是“最大80 RPS”。

按以下规则停止升压，保留证据并降到低负载观察恢复：

- 任一越权、重复提交、错误内容、OOM或容器异常退出，立即停止新请求/新任务。
- 60秒窗口内非预期错误率超过5%，连续两个窗口；或服务持续不可用30秒。
- 可用宿主内存低于15%、Docker内存使用接近额度90%并持续30秒、磁盘低于10 GiB，停止追加数据并保存资源样本。
- 正常混跑场景中，待执行任务连续3分钟净增长或等待超过5分钟，停止新任务并排空；明确的排队实验按独立任务数上限终止提交。
- 同机压测进程饱和或出现掉迭代，停止升档并核查施压能力。单纯CPU高不自动判失败，结合延迟、错误和到达率判断。

停止施压后最多观察5分钟恢复：普通接口回到同负载参考线、任务积压下降、Outbox排空。大任务允许继续到其20分钟执行预算内，单列最终状态和实际排空时间。默认worker租约90秒、恢复扫描10秒，因此强杀后不能要求立即恢复；无其他排队时可将120秒内观察到重新认领作为首轮参考，随后等待完成并对账。内存以空闲后是否趋于平台和多轮趋势判断，不要求RSS马上回到初值。

## 10. 实施顺序与现有命令

第一轮优先完成：环境指纹 → S0 → D1上的S1/S3 → S5/S6单任务 → S7干扰 → 候选负载三轮复测。第二轮补深分页、统计阶梯、扩worker、持续运行和故障恢复；避免一开始同时改变数据量、并发和副本。

以下是现有脚本的复用命令，需先准备 `.env.perf`、设置上述端口并确认当前终端可以访问Docker。命令会创建测试数据；已执行的验证与未完成场景见执行记录。

```powershell
# 在仓库根目录执行；.env.perf 已填写独立测试凭据和端口
$perfEnv = '.env.perf'
$perfProject = 'asset-amqp-perf'
$perfBase = 'http://127.0.0.1:59080/api/v1'

docker compose --env-file $perfEnv -p $perfProject up -d --build --wait --scale task-worker=1
if ($LASTEXITCODE -ne 0) { throw 'Compose startup failed' }

# 功能预检及首次账号初始化；产生的数据也需纳入种子清单
pwsh -File scripts/phase3-compose-smoke.ps1 -EnvFile $perfEnv -ComposeProject $perfProject -BaseUrl $perfBase
if ($LASTEXITCODE -ne 0) { throw 'Functional smoke failed' }

# 复用现有单次容量链路；它会新增10万行，正式重复对比需恢复同一初始数据集
pwsh -File scripts/phase3-capacity.ps1 -Rows 100000 -EnvFile $perfEnv -ComposeProject $perfProject -BaseUrl $perfBase
if ($LASTEXITCODE -ne 0) { throw 'Capacity check failed' }

# 在任务排空、记录本组结果后，再进行2副本对照
docker compose --env-file $perfEnv -p $perfProject up -d --wait --scale task-worker=2
if ($LASTEXITCODE -ne 0) { throw 'Worker scaling failed' }

# 完成采集并确认任务结束后停止本测试项目，保留命名卷供复查
docker compose --env-file $perfEnv -p $perfProject down
```

## 11. 结果模板和完成标准

| run_id | 代码/镜像 | 数据集/可见行数 | worker×slots | 场景 | 目标/实际RPS | 样本数 | p50/p95/p99 | 非预期错误率 | 掉迭代 | 完成任务/分钟、行/秒 | 峰值内存 | 对账 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 待执行 | 待记录 | 待记录 | 1×2 | 待执行 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待核验 |

任务明细另存：task_id、kind、文件行数/字节、预检耗时、确认耗时、确认到完成、执行日志耗时、下载耗时/字节、attempt、最终状态、committed、对账结果。并发批次的行/秒按“该批次成功处理总行数÷批次墙钟时间”计算，不把多个任务各自吞吐直接相加；生成吞吐与完整下载吞吐分别报告。

完成基线的条件：关键场景有三轮可比数据；统计与导入/导出对在线流量的影响有对照；至少一个稳定负载点和一个升压边界有证据（或明确尚未触顶）；资源与错误可关联；所有成功任务对账通过，未完成和失败任务有清单；结果能由相同数据、配置与源码复现。若观测不足，只记录现象和下一步验证，不能把猜测写成已确认瓶颈。

# P3：在线与异步任务资源竞争验收

2026-10-18：正式五组×三轮、并发配置探索、四任务扩容补测、独立功能/故障回归和最终恢复均已完成，证据审计见`data/perf/optimization-p3/acceptance.json`。主矩阵绝对门槛与 SQL 对账通过，**30% 相对参考线未全部通过：4/72 项超标**；“执行完成”不等于全部性能目标达标。

## 冻结条件

- 独立项目 `asset-amqp-opt`；应用镜像沿用 P2 的 `p2-observe`，未为本次结果更换业务代码或连接池上限。
- 复用 `20261016-local-baseline/s7base.dump`，校验旧导出 CSV 哈希；统计/在线/导入/导出使用四个不同 own 范围账号，不修改权限。
- 该快照在 D1 上预先为导出 owner 增加十万行，固定导出 101,901 行；不是纯 D1 的 320 RPS 数据状态。
- 在线 48 RPS，六类请求比例 35/25/15/5/10/10，预热 60 秒、稳态 300 秒；统计 0.2 RPS。保持旧 S7 的 VU 首请求登录协议和 MaxVUs64，以维持干扰对照可比性；P2 320 采用不同的全 VU 预认证协议，分开报告。
- 从在线到达时钟约 120 秒处触发后台任务，即稳态约第 60 秒。导入为十万行 Responsible F1，导出为相同冻结内容。
- 五组：纯在线、在线+统计、在线+统计+导入、在线+统计+导出、在线+统计+导入+导出。
- 当前单 Worker 双 slot 配置执行五组×三轮。单 Worker 单 slot 与双 Worker 双 slot 是单变量配置探索，各先执行一轮纯在线对照和双任务组；单任务本身不能使用额外 slot，故不为其重复探索矩阵。不冒充五组三轮稳定认证，扩容结果不计入最终“不做多实例扩容”容量。
- 宿主停止线依用户要求为可用内存 5%；增强采集器持续 30 秒才触发。原编排的启动/轮询资源预检仍即时检查同一 5% 下限；Docker 可用 10%/30 秒、磁盘 10 GiB 和全部业务门槛保持不变。

## 正确性和时间边界

每组前必须无非终态派发任务和未发布 Outbox，恢复同一个快照；组内在线新增、版本更新与 C 账号导入均逐项 SQL 对账。导出逐行内容摘要与旧冻结 CSV 一致，检查 owner 与下载权限。SQL 导入重对账在在线和统计客户端退出后执行，避免把验证查询当作 Worker 干扰。

双 slot 的双任务组必须观测到两任务实际 running，或有成功 Worker 日志证明执行区间重叠；仅同时存在 pending 不算并行。单 slot 的双任务组仍提交两项任务，按设计串行执行，独立记录排队代价，不伪称同时执行。

Task `create_to_complete` 包括请求、预检/确认、排队和轮询误差；Worker 成功日志 duration 用于估计真正执行区间。不能用二者的差值声称精确消息等待时间。若使用 `dispatch_wait` 指标，需要注明其从到期时间到认领时刻的边界，不能替代所有用户等待。

同机 CSV 生成、下载解析、客户端轮询和 k6 也消耗资源。全部启用相同观测，保留客户端进程 CPU/RSS、容器资源、数据库连接/锁/WAL 和服务池/GC 指标；不从某次 CPU 峰值或搜索增长直接推断唯一根因。

## 判定方法

每个接口以同轮纯在线作为对照：`(mixed_p95 / control_p95 - 1) × 100%`。各组绝对延迟/错误率/到达率/drops 使用旧门槛，30% 相对参考线单独判断。三轮四个混合组×六接口共 72 项。样本不足 100 不用于可靠 p95；统计每轮仅约 60 样本，保留原始结果，不把该接口单轮 p95当作可靠验收。

版本历史每组约 720 个样本，达到 p95 要求，但不足既定 1,000 样本的可靠 p99 要求；其他混合业务操作各组样本达到对应门槛时才引用 p99。不能用三轮 p99 的平均值或直接相加样本数来补足某一组的证据。

除了完整 300 秒的接口 p95，报告每分钟位置和后台实际窗口：短任务只占一部分稳态时间，整窗分位数可能稀释短时竞争。CPU 为单核 100% 的采样统计，Docker MemUsage 不等于 Go Heap/RSS；GC 和池等待累计量与包含它们的 HTTP span不能相加。未采到锁等待不证明从无锁竞争。

### 同机文件客户端证据

首轮单导出客户端的父进程约45.083秒，在所观测的36.397秒CPU计数区间消耗35.844 CPU秒，约98.48%单核，观测RSS峰值约199.39MiB；下载完成到父进程退出约40.294秒。该CPU统计不外推未采到的启动/结束边缘，与jobs自身Stopwatch编排44.072秒的边界不同。它直接证明同机CSV校验消耗了可观CPU，但不足以把每个HTTP延迟变化唯一归因于它。

## 独立最终功能及可靠性验收

证据目录：`final-validation-20261018T150400746/`。真实Go1.25.13的全包PG/AMQP回归、147项计数权限、七类CRUD/范围/软删除/乐观锁/版本和并发更新、七类CSV内容与匿名/跨owner下载拒绝均通过；1000行宽System Info导入成功。未以纯单元测试替代真实Compose故障：本次在观察到3000行提交后实际SIGKILL Worker，路由2次重复事件，租约恢复后attempt2完成十万行，幂等键/解析行/提交行/资产/版本均为100000，created92500＋skipped7500，无该任务死信、无未发布Outbox。kill前观察与实际kill存在间隔，7500重放不能误写成只提交过3000行。

全包日志中`TestPostgresPerformancePlans`按设计跳过，已由P1独立矩阵提供证据；`TestPublisherCrashChild`是父测试的专用子进程入口，父故障测试实际通过。没有运行Go race detector，也没有声称验证了全部Compose网络代理断响应；真实PG＋HTTP组件级响应丢失恢复测试与Compose进程强杀分别标识。

初次最终收口错误地要求死信队列绝对为零，触发工具门槛失败，原`state.json`保留。P3首帧即有历史`task-report-worker.dead=2`，主矩阵、探索及故障验证后仍为2；主队列ready/unacked为0。独立`acceptance-recovery.json`/`rabbitmq-audit-recovery.json`确认主队列清空、死信增量0，未清空或重放历史死信。四任务编排首次在该历史门槛处停止，尚未产生负载；经审计恢复后保留了`prior_controller`记录。

全部四任务补测结束后再次恢复原D1、通过147计数权限并核验运行配置；`post-scaling-quiescence.json`为Responsible总40001/活跃38010、全类型版本145002、活跃派发任务0、未发布Outbox0。`post-scaling-source-proof.json`确认110平台源文件及七个应用镜像仍与P2冻结版一致；`final-single-runtime.json`为一个Worker、两个slot。最终队列复核由独立只读收口执行并保存`post-scaling-queues.json`，主队列ready/unacked0、历史死信2且增量0。没有在补测后重复已通过的全包测试，应用源码未变，补测自己的SQL审计和最终恢复另有证据。

### 工具修正及原始证据边界

- 单比较时PowerShell输出JSON对象，多比较时为数组；离线汇总兼容两者，未改原比较文件。
- 原PowerShell JSON日期自动转换让双Worker探索的一条成功日志区间出现8小时时区误读。原case结果不覆盖；离线从日志原UTC字符串重算，重叠为2.867秒，并单列原值/偏差。数据库观测的两个running独立成立；主矩阵三轮区间复核仍为2.791/2.723/2.883秒。后续编排直接解析原日志UTC文本。

# P2 预认证业务容量实验（2026-10-18）

本实验由用户单独授权改变施压协议：所有可能使用的VU在正式计时前完成身份认证，从240RPS开始，不重复160RPS。旧P2的160认证、240失败、256VU诊断和CPU profile保持不变；新结果不与旧协议混为应用优化前后收益。

## 实现与不变项

新增`api-preauth.js`，派生自冻结`api.js`，旧脚本不修改。setup先创建与旧协议相同数量和归属的私有更新夹具，再为每个可能的VU单独登录。预热与稳态共两个场景，各最大128VU，因此预先建立256个不同服务端会话。按`idInTest`交付对应access token、principal、刷新时刻和refresh cookie，首次执行仅把cookie恢复到该VU自己的持久cookie jar；缺失/重复cookie、身份不匹配或VU越界直接终止。会话仅在k6进程内存中传递，不写入结果、日志或源码包。

cookie jar行为依照[Grafana CookieJar说明](https://grafana.com/docs/k6/latest/javascript-api/k6-http/cookiejar/)及[set接口](https://grafana.com/docs/k6/latest/javascript-api/k6-http/cookiejar/cookiejar-set/)，使用应用原有`asset_refresh`名称和`/api/v1/auth`路径。每个VU保留同步刷新逻辑，不共享刷新会话、不降低密码哈希成本、不扩大应用连接池。setup还检查全部会话可覆盖计划窗口并留30秒余量，不能覆盖则终止，不禁用刷新掩盖过期。

正式窗口仍执行Gateway、IAM逐请求授权、Asset业务处理和真实PG读写。此处“纯业务”仅表示初始登录准备移出到达率时钟，不代表跳过IAM鉴权或事务。新增窗口登录/刷新计数必须均为0，原业务比例35/25/15/5/10/10、延迟/错误/到达率/掉迭代/内容/SQL对账门槛保持不变。若实际发生刷新或登录，保留全部样本但不得认证为本协议的纯业务点。

`preauth-contract-test.mjs`直接执行新脚本的setup和会话函数，验证全部VU、独立cookie、最后一个VU、正常刷新、短TTL/缺失/重复cookie/身份边界；同时逐字比较实际business实现（仅允许ensureSession接收准备数据）和原阈值代码。真实k6先执行2RPS/10秒短冒烟，21次请求触及5%到达率浮点边界而未通过总判定，其认证/业务/SQL均通过；原始结果保留。随后独立4RPS/30秒冒烟通过，8个VU全部恢复独立cookie、窗口登录/刷新0。两次短冒烟均不提供可靠p95或容量认证，没有调整门槛。

## 复现与归档

入口：`pwsh -NoProfile -File scripts/perf/optimization-preauth.ps1`。归档为`data/perf/optimization-p2/preauthenticated-20261018/`，独立D1副本与k6版本记录、状态、原始结果、资源和慢SQL。旧归档不能覆盖；恢复仅用显式`-Resume`，会核对脚本哈希。

控制器验证实际运行的七个Go镜像ID与已验收P2相同，保持1Worker×2slots、search索引、原数据库与容器配置。每点恢复原D1快照；候选短测240/320/480/640/800，各预热60秒/稳态180秒，首个完整点失败后停止升压。对通过的最高候选执行独立三轮600秒稳态认证；普通性能失败可验证更低的已通过短点，但不会回到160。资源/健康/正确性失败直接停止。

本轮不运行应用构建或Go测试与压力并行。应用未修改，沿用冻结P2镜像功能回归；新增工具由契约检查和真实HTTP/SQL冒烟验证。额外会话和setup数据复制会增加施压端时间/内存，必须如实记录k6 CPU/RSS，不能将协议差异算成应用优化收益。

### 用户授权的资源停止线变更

240及320短测仍采用原宿主可用内存15%持续30秒停止线。用户在运行中要求降为5%，若需重启则在下一档实施；320已启动，因此保持其完整窗口，在320完成后、480开始之前优雅退出原采集器并启动新采集器。2026-10-18 16:20:28新配置生效，没有中断k6或为切换额外重启应用；各点常规D1恢复仍照常执行。

从480及后续测试起，宿主停止线为**可用内存低于5%持续30秒**，run预检也读取独立`resource-policy.json`的5%；Docker可用内存10%/磁盘10GiB、HTTP/错误率/到达率/掉迭代门槛均不变。切换记录含旧/新PID、脚本哈希、时间和已完成run，见`resource-policy-handoff.json`，各次采集配置及api_started事件亦记录实际阈值。这是用户要求的环境条件变化，单独标记，不归因为应用性能优化，也不改写旧15%结果。

默认脚本仍为15%；新实验要采用5%须在独立归档中显式提供resource-policy.json，并以新采集器参数`-MinHostFreeMemoryRatio 0.05`启动。正式脚本/采集器已有记录时，Resume会验证业务脚本不变；仅经过审查的资源政策调整可另用`-AcceptResourcePolicyChange`记录runner/collector哈希修订。不要用该开关接受业务逻辑、阈值或失败统计变化。

- 480的Asset→IAM授权累计114602次，恰为预热28801加稳态85801次业务请求，均值2.267ms；IAM授权SELECT均值0.534ms、部门WITH0.550ms。没有通过跳过逐请求鉴权获得吞吐。这些服务器计数/耗时来自实际采样边缘，不能与嵌套SQL相加或当作HTTP p95。

**已证实**：正式窗口无首次登录/刷新，240及320短测通过，320三轮稳定，480在本机当前配置出现明显延迟及到达率拐点，Asset池确有明显排队。**有证据支持**：搜索SQL、Asset连接占用、PG与k6共享CPU压力共同参与延迟增长。**未确认**：谁是唯一底层瓶颈、扩大池会否有效、迁出k6后480是否可通过、系统真实最大RPS。客户端128VU已满是丢弃的直接机制，不能仅凭这一条判定服务上限，也没有盲目增加VU或连接池继续升压。

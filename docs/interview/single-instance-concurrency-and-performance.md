# 本系统单实例并发能力：实测口径、用户规模推算与面试讲解

最新补充日期：2026-10-19。第0节为新增极限吞吐实验；第1节及后续正文保留2026-10-18的P0–P3验收版口径，其中“480短测未通过、640/800未执行”限定于当时128 VU协议。新实验和原结果均完整保留，不能混为一次测试。P3仍有4/72相对参考线超标；本文不是生产容量承诺，也不证明个人参与范围，面试只陈述实际负责的工作。

## 0. 2026-10-19极限吞吐：新增证据与面试解释

**当前仍只能把320 RPS称为最高已验证稳定负载；本机短测最高成功处理速率已观察到约566.47 RPS。两者回答不同问题。** 新实验没有扩容服务实例或连接池，也没有改变业务请求、权限和持久化，而是增加施压端预认证VU，扩大固定到达率矩阵。

此次九个有效完整点共1259198次稳态业务请求全成功，SQL增量对账全部通过。480长测前六分钟维持480 RPS，最后一分钟降到458.53 RPS，版本p95升至1083.28ms；不能截取前三分钟来宣传持续能力。520/480各第一轮已失败，按原执行器规则未继续第二、三轮，不是“三轮失败”。

“为什么请求都成功，测试仍不通过？”可以回答：固定到达率模型要求按计划启动请求。业务错误率衡量已经发出的请求，drops代表没有发出的到达机会，延迟门槛则衡量用户等待时间；三者需要分别满足。拿286321次成功请求证明480长测业务可靠是合理的，拿它证明480稳定则不合理。图中的每秒成功数沿用原稳态归属请求/计划时长口径，饱和窗口含有界收尾，并非逐请求完成时刻流。

“瓶颈是不是数据库？”可以回答：Asset池达到10/10，640档保守业务区间累计连接等待约21092秒，IAM仅约20秒，说明Asset数据库访问链路明显排队；同时PostgreSQL、k6和宿主CPU都很高。累计等待是多个请求的总和，不能当单次延迟。增加到512 VU又触发客户端内存保护，所以当前证据支持共享CPU、Asset池排队及施压端限制共同存在，还没有单变量实验能宣布唯一瓶颈。下一步先独立施压，再验证池预算或慢搜索优化。

“到底能给多少用户用？”仍应从稳定证书推算：若每名活跃用户平均每5秒产生一个业务HTTP请求，320×5≈1600名；若每10秒一次，则约3200名。480×5≈2400、566.47×5≈2832仅是短时请求需求换算，不能作为稳定支持人数。本次480长测已失败，尤其不能宣传稳定支撑2400人。既未验证这些数量的独立身份，也没有把浏览器多接口调用、集中登录和瞬时集中请求纳入此人数模型；注册用户数不能由RPS推算。

一分钟版本：“我用Go、PostgreSQL和RabbitMQ构建资产治理平台，并用真实权限、真实写入的80%读20%写混合负载验收。单套服务实例在十万条D1数据下，320 RPS经过三轮十分钟认证。后来把施压端身份认证前置并增加VU，480和520三分钟都能零丢迭代通过；继续升至目标1000 RPS后，实际吞吐在约550到566 RPS平台，所有发出请求成功，但丢迭代和尾延迟不合格。更重要的是480和520十分钟测试在后半段退化，因此我没有把峰值当稳定容量。观察到Asset池排队、共享CPU以及k6内存限制，下一步用独立施压机把客户端和服务端因素拆开。这些结论都有原始指标、SQL对账和恢复记录。”

详细数据、曲线及复现命令见[2026-10-19极限吞吐报告](../testing/extreme-throughput-results-2026-10-19.md)。以下为10月18日验收版材料，所有数字保留其当时协议条件。

## 1. 先说清楚“单实例”

这里指 Gateway、IAM、Asset、Task Report、Publisher、Worker 等服务各运行一个进程/容器，Worker 当前有两个执行 slot。PostgreSQL、RabbitMQ、MinIO 也各一个实例。整个系统是多个服务组成的单套部署，不能描述成“一个 Go 进程实现全部能力”。Go 服务内部正常使用多个 goroutine 和 CPU 核心；没有通过增加服务副本提高这组容量数据。

测试主机为 i5-12400F、12 个逻辑处理器、约 31.86 GiB 内存；Docker 可见 12 个逻辑处理器、约 15.55 GiB 内存。容器没有设置独立 CPU/内存硬限额。k6、文件测试客户端和其他实验共享宿主机，所以结果包含客户端与宿主资源竞争，不能直接外推为生产硬件容量。

## 2. 当前可以直接引用的业务处理能力

**D1 数据集、身份认证在计时前完成的混合业务协议下，最高已验证稳定负载为 320 RPS。三个独立的 600 秒稳态窗口共 576,002 次请求全部成功，dropped_iterations 为 0。** 每轮先恢复同一 D1 快照，再预热 60 秒；三轮的写入与版本增量均通过 SQL 对账。

320 是已验证稳定点，不能说成系统最大 RPS。480 RPS 短测有 600 次丢弃迭代，实际约 476.67 RPS；即使已经发出的请求全部成功，该档位仍未通过。320 到 480 之间已观察到明显排队和延迟上升，但没有以更细档位测出精确拐点或最大吞吐，640/800 没有继续执行。

## 3. RPS、HTTP 并发、VU、活跃用户、注册用户怎么区分

| 概念 | 含义 | 本系统能否给出结论 |
| --- | --- | --- |
| RPS | 每秒完成/发起多少业务 HTTP 请求，需要注明实际值和到达模型 | 同条件下实际稳定约 320 RPS |
| 平均在途 HTTP 请求 | 同时处于所定义 HTTP 服务边界内的平均请求数 | 可用稳定均值计算；不等于并发上限 |
| 瞬时并发请求上限 | 同一瞬间大量请求到达时还能否满足 SLA | 没有做独立同步突发连接/请求认证，不能报确定人数 |
| k6 VU | 客户端执行请求的虚拟用户资源 | 每个场景配置 128 上限；两个场景共 256 会话，不等于服务器最多支持 128/256 用户 |
| 已登录会话数 | 用户可能已登录但没有请求 | 本次预建了 256 个会话；未验证数千独立会话下的容量 |
| 活跃交互用户 | 一段时间内反复操作，操作之间存在思考/阅读时间的人 | 可以按显式交互假设推算，尚未进行同人数真实用户模型测试 |
| 在线浏览人数 | 页面可能打开但长时间不请求，或存在轮询 | 取决于请求频率；不能仅按打开页面人数估算 |
| 注册用户/企业员工数 | 账号存量 | 与同时活跃比例、权限结构、会话和数据库规模有关，不能从 320 RPS 直接反推 |

例如一千人都打开页面但每人十秒才产生一个请求，平均约 100 RPS；一千人在同一毫秒各发出一个请求则是另一种突发。前者可能符合本次容量预算，后者没有被本次固定到达率测试证明。

## 4. 用实测均值计算平均在途请求

对于相同统计边界、足够稳定的系统，Little 关系为：

\[
L=\lambda W
\]

其中 L 是平均在途请求数，λ 是实际请求完成速率，W 是平均 HTTP 耗时（秒）。这是平均数量的关系，不给出瞬时峰值或极限容量。

从三轮全部成功的 576,002 次请求计算 `Σ(操作请求数 × 操作平均耗时) / 总请求数`，混合平均 HTTP 耗时为 **7.5538 ms**。不是平均 p95，也没有把内部鉴权/SQL 耗时重复加进来。

| 轮次 | 实际 RPS | 平均 HTTP 耗时 ms | 该 HTTP 边界平均在途数 |
| --- | ---: | ---: | ---: |
| 1 | 320.0017 | 7.5201 | 2.4064 |
| 2 | 320.0017 | 7.1347 | 2.2831 |
| 3 | 320.0000 | 8.0067 | 2.5621 |

这说明请求大多很快完成，固定到达率下平均只需少量 HTTP 请求同时在途；**不能据此说系统“仅支持 2–3 人并发”，也不能反向说支持 320 个同时在途请求。** 一个用户阅读页面时不占用 HTTP 处理中的请求位置。TCP keep-alive 连接、浏览器渲染和用户阅读不在这里的 HTTP duration 边界里。

## 5. 从业务频率推算活跃用户人数

设每人一次操作产生 m 个顺序业务 HTTP 请求，操作完成后平均思考 Z 秒；每个请求平均耗时 R 秒，则平均一个用户的操作周期约为 `Z + mR`。N 个这样的用户对应：

\[
\lambda_{HTTP}=\frac{Nm}{Z+mR},\qquad
N=\frac{\lambda_{HTTP}}{m}(Z+mR)
\]

若页面并行请求、后台轮询或一个操作对应不同读写比例，需要重新建模；不能把 `mR` 套在并行请求的页面完成时间上。这里借用 320 RPS 实测 R≈0.007554 秒，仅为同业务分布的理论推算，R 随负载和数据范围改变，未进行这些用户人数的闭环实验。

如果 m 个请求中包括全局统计、文件上传、导出下载或任务状态轮询，就不再是原六类请求的相同分布，需要测量新的平均耗时和资源成本。闭环模型中，响应变慢也可能使“等待中的用户数”增加；这不代表容量优化，因此用户数推算必须与吞吐、尾延迟和错误/丢迭代门槛一起使用，不能靠延长等待来宣称支持更多用户。

为了让面试表达有业务意义，可以同时列出“按已验证负载的理论值”和“预留 30% 吞吐余量的规划示例”。后者采用 **224 RPS=320×70%**，是说明容量预算的例子，不是放宽压测门槛或经新实验认证的生产 SLA。

| 1 秒 | 1 | 322 | 226 |
| 2 秒 | 1 | 642 | 450 |

适合面试的具体表述是：**“如果用户平均五秒操作一次，而且一次只产生一个与测试分布相同的业务请求，一千个活跃用户约产生 200 RPS；从本次 320 RPS 稳定点看，这个流量在理论预算内。若一次操作要发两个请求，同样一千人就接近 400 RPS，超过当前已验证稳定点，不能承诺。这里说的是带思考时间的活跃用户估算，不是一千个 HTTP 请求同时执行的实测结论。”**

如果面试官给出“企业有一万员工，能不能用”，应该先询问峰时活跃比例、操作频率、页面请求数量和后台任务量。例如“一万员工、峰时 10% 活跃、每五秒一次且每次一个请求”与上面一千活跃用户的假设相同；10% 是业务输入，不是本系统压测测得的比例。批量列表刷新、搜索热词和全局权限用户比例变化也会改变结果。

身份样本边界也必须说明：本次 P2 为 **13 个业务账号创建 256 个独立会话**，并没有生成一千或两千个不同业务身份来测 IAM、会话存量和权限数据分布。因此上述用户数不能宣称已验证了同人数的登录、Token 刷新或权限冷启动；扩展独立账号池、使用真实页面请求组合和更长稳态，是将理论估算转为用户规模认证所需的后续实验。

这里256指供预热/稳态VU使用的会话；夹具准备另有13次登录，完整setup合计269次登录。两个场景分别有128个VU容量，按预热、稳态先后运行，不是实测了256个HTTP请求同时在途。

## 5.1 480 RPS 也代表真实处理能力，但需要换一个准确口径

用户补充要求：同时分析 480 RPS，因为已发出的业务请求全部成功。这一点应当正面呈现，不能因为单项到达率门槛未通过，就抹掉已经完成的真实业务工作量。

| 项目 | 320 RPS 稳定认证 | 480 RPS 边界实验 |
| --- | ---: | ---: |
| 稳态窗口 | 3 × 600 秒 | 1 × 180 秒 |
| 实际完成速率 | 各轮约 320 RPS | 476.6722 RPS |
| 已发出业务请求 / 成功 | 576,002 / 576,002 | 85,801 / 85,801 |
| 已发出业务请求错误率 | 0 | 0 |
| 未能启动的迭代 | 0 | 600 |
| 原绝对 HTTP 延迟门槛 | 通过 | 通过 |
| 原零丢迭代门槛 | 通过 | 未通过 |
| 是否有三轮稳定认证 | 有 | 没有 |

该实验说明：**在不增加服务副本、保留实际授权和写事务的条件下，系统确实短时完成了接近 480 RPS 的混合业务请求，已发出请求全部成功。** 更完整的口述是“目标 480 RPS 的三分钟实验，实际完成约 476.7 RPS，8.58 万次已发出的请求全部成功；同时有约 0.69% 的计划迭代未发出，因而把它记为边界处理能力，而不是三轮通过的稳定承载量”。

`85801 + 600 = 86401` 是按已发出与 dropped 重建的到达机会数；600/86401≈0.6944%。`480×180=86400` 与这个数差 1，属于窗口端点计数；实际 RPS 与目标的差距约 0.6933%，两个比例的分母不同，不应强行写成完全一样。**丢迭代不是 HTTP 失败**：它们根本没有发到服务器，所以不能计为 HTTP 500；但也不能从已发出的成功率中推断全部计划需求都已得到服务。

这组 p50 仍低，但尾部显著拉长；不能只挑中位数描述“几毫秒响应”。三个稳态分钟的实际速率约为 480、480、470.02 RPS，列表 p95 约 33.93、32.64、233.07 ms，搜索 p95 约 125.89、131.72、309.00 ms。600 次 drops 集中在后段，说明整窗平均会掩盖后段排队。前两分钟曾维持完整 480，到第三分钟开始出现较明显压力，因此不宜将三分钟现象外推为全天稳定。

480 档的混合加权平均 HTTP 耗时约 **26.3350 ms**。按“已完成请求的耗时总和/180 秒”描述，约相当于 **12.55 个 HTTP 请求时间单位同时占用**；由于后段非平稳及跨窗口请求边界，这只是近似平均占用解释，不是稳定系统的并发上限认证。不能把 480×p95 当作“支持多少并发用户”。

## 6. 异步任务并发与在线请求容量分别计算

在线业务 RPS 不能直接换算成每秒可完成多少个十万行导入。创建/确认任务快速返回不代表导入完成。当前单 Worker 双 slot 允许最多两个任务执行槽位；RabbitMQ 可以缓冲待执行消息，但排队不是无限容量，也不意味着任意等待时间都有保证。

任务至少包含上传/预检、确认、Outbox 发布、消息等待、原子认领、CSV 处理、逐批资产事务、进度更新；导出还包括读取、编码、上传 MinIO 和受权下载。`create_to_complete` 是包含排队和客户端轮询误差的生命周期，Worker 成功日志的 duration 是执行区间估计，不能混用。

P1-B 已验证单个普通 F1 十万行导入中位约 17.028 秒、约 5,872.6 行/秒；宽 System Info 十万行约 52.343 秒、约 1,910.47 行/秒。这是不同类型/宽度，不能相互比较为吞吐下降百分比。普通导入新增索引和字节分批后存在写入成本，不能把所有路径都包装成提速。

P3 已用原冻结 S7 快照、48 RPS 在线流量和 101,901 行固定导出，完成五组三轮后台竞争验证。216,010 次在线请求和 726 次统计请求全部成功、零丢迭代，6 项导入与 6 项导出全部成功、资产和版本对账通过；72 项相对 p95 比较仍有 4 项超出 30%，均是第 1、3 轮导入组创建/更新，绝对 p95 约 11.40–11.94 ms。因此“绝对门槛通过”与“相对干扰没有全部解决”应同时说明。

纯在线搜索 p95 为 11.05–11.69 ms，导入组为 11.13–12.36 ms，双任务组为 11.13–12.72 ms；这组搜索相对比较均通过。普通十万行导入在在线干扰场景中的生命周期中位约 21.46 秒，双任务组约 22.81 秒；固定导出中位约 4.06 秒和 4.00 秒。这些是每组 3 项任务的描述性中位数，不是 p95，也不是两个同时导入的聚合吞吐。

该快照在 D1 上额外准备了十万条导出 owner 的资产，与纯 D1 的 320 RPS 测量不是同一个数据状态。**没有做“320 RPS 在线 + 持续十万行任务”的稳定认证，所以不能把两组结论拼成这个承诺。**

异步任务的可持续到达率应低于实测完成率，且必须满足队列等待目标。两个 slot 的吞吐不能简单等于单任务吞吐乘二，因为共享 Asset 连接池、PostgreSQL、WAL 和 CPU。扩 Worker 前必须同时观察在线尾延迟与后台完成时间。

本次还补齐了有真实在线流量的四任务对照，以下均为**单轮探索**，普通Responsible F1，每个任务十万行，在线48RPS；不是纯D1的320RPS负载：

| --- | ---: | ---: |
| 真正执行的Worker / 重叠任务峰值 | 1 / 2 | 2 / 4 |
| 四任务处理窗口 | 52.095秒 | 37.014秒 |
| 聚合导入吞吐 | 7678.25行/秒 | 10806.79行/秒 |

八个任务全部成功、各自十万行资产/版本/幂等键核对通过。增加Worker后该批次吞吐约增加40.75%，但PG CPU采样峰值222.69%→538.12%（单核100%），增加了资源竞争，也没有线性翻倍。单轮不能代表所有数据宽度和任务组合。最终部署已恢复为一个Worker双slot；上述不扩容列可作为面试中的具体异步能力实例，扩容列只说明实验对照，不混入单实例容量。

另一个有用取舍：一个Worker改为单slot，双任务组导出生命周期约22.48秒，而双slot约3.64–4.44秒，在线未显示必须降低slot的收益，因此保留双slot。最初仅用两个任务测试两个Worker时任务落在同一个Worker，证据不足；随后用四任务确认两个不同Worker和四项执行重叠，才形成上面的有效分担对照。

## 7. 面试时怎样解释优化的收益和代价

### P0：先消除数据移动，而不是直接堆并发

原全局统计为了计数，逐类分页 Export 完整记录。七类合计一次统计有 20 次内部请求、约 103 MB 响应体传输，然后反序列化并计算长度。改造后由 Asset Service 内部复用数据范围和软删除条件，用一条聚合 SQL 返回七类计数；Task Report 不直接跨服务查询资产数据库，继续保留授权和统计快照。

同条件 global 0.1 RPS 的中位数由 6,263.47 ms 降到 16.66 ms；两边各 25 个样本，只作为描述性中位数比较。新版 global 1 RPS 有足够样本，p95 26.66 ms，达到原 5 秒目标。不能拿旧低样本 p95 与新不同档位 p95 计算收益。

### P1-A：根据执行计划分解排序、扫描和 JSON 转换

列表先确定有序页键，再关联取业务字段，避免对最终会被 OFFSET 丢弃的行进行完整 JSON 转换；为主要权限条件和排序建立经过独立实验验证的部分复合索引，针对实际搜索条件评估 pg_trgm/GIN，而不是给所有字段机械加索引。保留旧 Offset API，没有宣称已经上线 Cursor 分页。

同 D1、80 RPS、600 秒的对照中，列表 p95 191.445→5.245 ms，搜索 137.577→68.792 ms；末页 limit20/offset38000、20 RPS 的 p95 351.004→12.487 ms。单条 EXPLAIN 变快不是 HTTP p95 自动变快的证据，所以两类证据都保留。GIN 和排序索引增加空间与写入工作，普通导入并非同步变快。

### P1-B：按真正的线大小分批，保留可靠事务

固定 500 行的宽记录在内部 JSON 后可能超出 Asset Service 的 1 MiB 限制。改为最大行数与实际序列化字节双约束，包含 JSON 编码膨胀和信封开销，并预留余量；单行过大明确失败，没有无限提高请求体上限。

保留 task_id+row_key 行级幂等，单批中幂等键、资产和版本一起提交。Worker 持有有效 execution token 更新进度，重启后重放已提交行不会重复创建资产或版本。AMQP 是至少一次投递；可以说“通过幂等实现业务副作用去重”，不能称 exactly-once 传输。

### P2：区分认证突发、业务排队、数据库和客户端竞争

HTTP 指标按规范化路由采集，数据库记录查询/COPY/连接获取与 pgxpool 统计，IAM 上游耗时覆盖响应体消费，运行时采集 goroutine、heap、GC、进程 CPU/RSS；任务链区分发布/认领等待和执行阶段。没有将动态资产 ID、Token、task_id 放入指标标签。pprof 只在一次受控诊断中临时开启，随后关闭。

原首次登录协议中的 IAM bcrypt 热点有独立受控 profile 证据，但没有降低密码哈希成本。全部 VU 预先认证后仍在 480 观察到 Asset 池达到 10/10、10,840 次成功空池等待，累计约 840.103 秒；这是并行等待累加，不是单个请求等 840 秒。同期有大量慢搜索和 PostgreSQL/k6 CPU 压力，支持近端排队和共享资源竞争的判断，尚不支持“数据库就是唯一瓶颈”。IAM 池压力明显小于 Asset，不能把所有延迟归因于鉴权。

## 8. 可直接口述的版本

### 约一至两分钟

“我的系统采用 Go、PostgreSQL、RabbitMQ 和 MinIO，按 Gateway、IAM、资产和任务处理拆分。容量验证时每个服务只有一个实例，没有横向扩容。使用十万资产的冻结数据集，按列表、详情、搜索、版本、创建和更新的真实混合比例施压，提前完成所有测试 VU 的身份认证，但保留每次请求的授权和数据库事务。320 RPS 做了三轮各十分钟，累计 57.6 万次请求全部成功且没有丢迭代；列表 p95 约 8 到 11 毫秒，搜索约 100 到 104 毫秒。目标 480 RPS 的三分钟实验实际完成约 476.7 RPS，8.58 万次已发请求也全部成功，不过约 0.69% 的计划迭代未能发出，因此把它记为短时边界处理能力，稳定认证仍是 320 RPS。

“320 是最高已验证稳定负载，不是最大吞吐或 320 人同时在线。若用户每五秒操作一次、一次一个请求，一千活跃用户约 200 RPS，只能作为同业务假设下的理论估算。后台十万行任务单独测吞吐，还要在在线流量下检查干扰，不能把异步接收快当成任务完成快。”

### 约三分钟的展开顺序

1. 讲业务与可靠性边界：配置驱动的七类资产、IAM 数据范围、软删除/乐观锁/版本，任务 Outbox/Inbox、原子认领、租约 token、手动 ACK、行级幂等。
2. 讲测试可信性：同一 D1 dump、相同账号与比例、固定到达率、预热/稳态分离、独立三轮、原始结果与 SQL 对账；没有只展示一轮最好数。
3. 讲两个确定收益：统计减少完整数据搬运，列表推迟全字段转换并匹配权限排序索引；同时承认写入索引代价。
4. 讲一个正确性优化：宽记录按编码字节分批，故障后幂等恢复，服务请求体安全边界保留。
5. 讲瓶颈证据：集中首次登录有 bcrypt profile，预认证后 480 仍有 Asset 池等待、慢搜索及 CPU 竞争；不直接加池或堆 Worker。
6. 讲用户数推算的假设，再说明 P3 的线上/后台干扰实测和未测的上限。

## 9. 常见追问与准确回答

**“你说支持一千人，是一千并发吗？”**

不是一千个请求同一瞬间在途的实测。它是每人五秒一次、每次一个业务请求的一千活跃用户模型，约 200 RPS；瞬时突发、独立会话数和浏览器页面 fanout 需要另外验证。

**“Go 协程很多，为什么只测到 320？”**

goroutine 数不是端到端容量。每次请求还要经过鉴权、共享连接池和数据库查询/事务；搜索、WAL、GC、网络及同机施压端都会影响排队。本次 480 的失败包含 Asset 池等待和共享 CPU 压力，320 也不是已经证明的极限。

**“连接池 10 为什么不直接调到 100？”**

池等待说明这里形成队列，但队列可能是下游 SQL/CPU 已承压的结果；直接放大池可能把压力推给 PostgreSQL，增加并行扫描和尾延迟。需要一次只改一个变量，在相同负载下比较查询时延、CPU、锁/WAL与在线 SLA；本次没有用未经验证的扩池宣称收益。

**“你做了缓存吗？”**

本次没有新增资产结果缓存来绕过查询与数据权限。主要收益来自避免全量数据传输、减少排序/反序列化及合适索引。PostgreSQL/OS 的缓存自然存在，实验保持相同恢复和预热，不能称数据库冷盘测试。

**“三轮十分钟能代表全天稳定吗？”**

只能支持所测窗口、数据集和场景下的稳定结论。长时间持续写入、token 刷新、autovacuum、磁盘增长、队列积压与 D2 更大数据规模都需要补测。历史 48 RPS 一小时通过可以单独引用，不能替代 320 RPS 长稳态验证。

**“Worker 宕机会丢数据吗？是否 exactly-once？”**

消息是至少一次投递，手动 ACK 在业务处理后进行。Outbox 保证任务派发事件可恢复，Inbox/原子认领及 execution token 限制重复执行和过期写入，资产单批事务绑定行幂等键与版本。已有真实 Worker SIGKILL 和消息重投恢复证据；事务提交后 HTTP 响应丢失另有真实数据库+HTTP 组件测试。不能把组件级断连接测试描述为所有 Compose 网络故障都已注入验证。

**“这是不是生产可上线的完整安全验收？”**

不是。性能改造的权限范围/统计/读路径和可靠性回归有明确证据，但既有删除/恢复范围检查及敏感版本字段存在独立审计待办。没有把尚未覆盖的场景写成已通过，也不能从本机性能验收推导生产安全、HA 或灾备已经完成。

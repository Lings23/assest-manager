## 阶段目标与结果

阶段一没有继续扩展旧系统业务，而是同时完成两项工作：

1. 对仍承担实际业务的 Go、SQLite、嵌入式前端旧系统进行安全止血，降低 SQL 注入、持久化 XSS、弱默认凭据、Token 泄露、越权和导入滥用风险。
2. 建立可独立演进的新平台 Monorepo、服务边界、前端、API 契约、容器编排和精简 CI，为阶段二实现 IAM 与元数据资产引擎提供稳定起点。

阶段一退出条件已经满足：旧系统安全回归通过，新平台五个 Go 进程和 Vue 前端可构建，OpenAPI 生成一致，Compose 全栈运行验收通过，可达依赖漏洞为零。阶段二可以开始。

## 采用的方案与选择理由

| 方案 | 选择理由 |
|---|---|
| 旧系统功能冻结，新业务进入 `platform/` 与 `apps/web/` | 避免在迁移期继续扩大旧架构债务，同时保留当前业务连续性和回退路径。 |
| Go workspace + 多进程模块化单仓库 | 小团队仍可共享工具和契约，又能按 gateway、IAM、资产、治理、任务报表明确领域边界；比立即拆成多个仓库更低成本。 |
| Vue 3 + TypeScript + Vite | 提供组件化、类型检查和现代构建能力，替代难以维护的单页嵌入脚本。 |
| OpenAPI 作为公共契约并生成 Go 路由清单 | 让网关、后端和前端围绕同一接口基线演进，CI 可检测契约与生成产物漂移。 |
| PostgreSQL Schema 隔离领域数据 | 在单一数据库运维成本下保留服务数据边界，适合当前团队规模，并为以后独立拆分保留空间。 |
| RabbitMQ + MinIO | 分别为后续异步任务、导入导出和对象文件提供标准基础设施，避免在阶段二临时引入不一致方案。 |
| Docker Compose 固化本地集成环境 | 用一条命令复现基础设施、服务和前端，降低小团队环境差异和联调成本。 |
| PR 快速检查、`master` 完整检查 | 在保留基本质量门槛的同时压缩日常反馈时间，避免为小团队引入过重发布流程。 |

## 已完成能力

### 旧系统安全止血

- 七类资产统一执行字段白名单、类型和条件校验，拒绝系统字段及未知字段写入。
- 更新权限与数据范围进入同一 SQL 条件，降低越权和竞态风险。
- 统一 HTML 转义和安全响应头，修复主要持久化 XSS 展示路径。
- Access Token 仅保存在内存；JWT 增加算法、issuer、JTI 和到期约束。
- 移除固定默认管理员密码，支持部署密码和首次启动随机密码。
- 增加登录失败限制、注销/改密撤销、统计错误处理及 SQLite WAL 稳定性配置。
- 导入增加大小、文件类型、字段和值校验，并明确部分成功结果。
- 明确 `admin` 与 `reporter` 的权限矩阵。

### 新平台工程基线

- 建立 gateway、iam-service、asset-service、governance-service、task-report-service 五个 Go 进程。
- 建立统一配置、结构化日志、请求 ID、错误信封、CORS、安全头、健康检查、超时、恢复和优雅停机能力。
- 建立 Vue 3、TypeScript、Vite、Pinia、Vue Router、Element Plus 前端。
- 建立 `/api/v1` OpenAPI 契约、生成工具及漂移检查。
- 建立 PostgreSQL、RabbitMQ、MinIO、五个服务和前端的 Compose 编排。
- 建立精简 CI、依赖安全检查、密钥扫描、配置扫描和 Dependabot。
- 固化旧系统冻结规则，阻止阶段二继续向旧系统增加常规功能。

## 验收基线

阶段一已经验证：

- 旧系统与新平台 Go 单元测试、回归测试、`go vet` 和构建通过。
- Vue 类型检查、单元测试和生产构建通过。
- OpenAPI lint 与生成一致性检查通过。
- Compose 完整构建、启动、健康检查、网关转发和前端访问通过。
- `govulncheck` 未发现可达 Go 漏洞，`npm audit` 为 0 vulnerabilities。
- 密钥扫描未发现泄露。

当前完整 CI 唯一已接受例外为 `apps/web/Dockerfile` 的 Trivy DS-0002：开发/测试 Web 容器暂未声明非 root `USER`。该问题不阻塞阶段二研发，但必须在生产或公网部署前修复并重新通过容器配置扫描。

## 阶段二交接

阶段二在 `develop` 分支开展，新功能只进入新平台目录，旧系统继续执行功能冻结。建议按以下顺序推进：

1. 建立 IAM 数据模型、非对称签名、短期 Access Token、持久化 Refresh Token、轮换和重复使用检测。
2. 将角色、权限、部门和数据范围策略落入服务端授权模型，并完成业务方权限确认。
3. 建立资产类型、字段 Schema、校验规则和版本管理，形成元数据驱动的资产引擎。
4. 实现责任部门等基础主数据及可审计的变更路径。
5. 把部署密钥接入目标环境的密钥管理，补充阶段二集成测试和契约测试。

密钥管理和权限矩阵确认不阻塞 `develop` 分支创建，但分别是目标环境部署和 IAM 功能验收的前置条件。
